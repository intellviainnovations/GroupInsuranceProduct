# ADR-0002: Persistence rules, sessions, jobs and audit

- **Status:** Proposed (database choice is Decided in ADR-0001; the rules below are the architect's recommendation, awaiting the product owner's say-so)
- **Date:** 2026-10-18
- **Deciders:** product owner, tech lead

## Context
The product database holds every sale after it happens: customer and nominee data, insurer proposals and certificates, money postings, documents and the audit trail (D-023). It must be correct under partial failure (customer debited but policy not issued), auditable for the bank, and portable enough to run on the pilot bank's Oracle 19c if required (ADR-0001, Q16). Data model: `docs/design/data-model.md`.

## Decision
### 1. Portable SQL rules (Proposed)
| Rule | Reason |
|---|---|
| Table and column names: `snake_case`, singular tables, at most 30 characters, no quoted or reserved identifiers | Oracle-safe |
| Primary keys are UUIDs generated by the application (SQLAlchemy `Uuid`); internal sequence numbers only where order matters (audit) | No database-specific identity features |
| Money is `NUMERIC(14,2)` in INR; never float. Rates and percentages `NUMERIC(7,4)` | Exactness |
| Timestamps are stored in UTC (`TIMESTAMP WITH TIME ZONE`); business dates use `DATE`; display in IST in the UI | Oracle `DATE` carries a time part, so be explicit |
| Booleans use SQLAlchemy `Boolean` (a flag column with a check constraint on Oracle) | No native boolean in Oracle 19c |
| **Empty string is stored as NULL.** The adapter layer normalises empty strings from every insurer and bank API | Oracle treats `''` as NULL; keeps behaviour identical on both |
| Enumerations are `VARCHAR` plus a `CHECK` constraint, or a reference table | Portable |
| No JSON/array/range columns, no `ON CONFLICT`, no partial or expression indexes, no database triggers for business logic | Portable and easier to review |
| Large text/binary: `TEXT`/`BYTEA` in PostgreSQL map to `CLOB`/`BLOB` through SQLAlchemy types | Oracle limit of 4000 bytes on `VARCHAR2` |
| Queue claiming uses `SELECT ... FOR UPDATE SKIP LOCKED` through SQLAlchemy | Exists in PostgreSQL, Oracle and MySQL 8 |
| Every migration is backward-compatible (add before remove) | The bank cannot hot-patch (D-007) |
| CI runs the test suite on PostgreSQL always, and on a second database before any port is promised | Proves portability |

### 2. Sessions (Proposed)
Server-side session rows in the database; the browser holds only an opaque 256-bit random id (stored hashed). Idle and absolute timeouts, rotation on login, revocation on logout. No Redis. Revisit if load testing shows the database is the bottleneck.

### 3. Jobs and idempotency (Proposed)
A `job` table with `run_after`, attempt counters and `dedupe_key`, drained by an in-process worker. Every outbound money or insurer call carries a unique reference we generate, and an `unknown outcome` result (timeout, connection drop) is reconciled by reading the remote state before any retry. No retry of a debit without that check.

### 4. Audit (Proposed)
Append-only `audit_event` table with a hash chain (each row stores the previous row's hash). The application database role has insert-only rights on it. Events: authentication, role changes, every enrolment status change, approvals, money postings, insurer calls, administrative actions. No personal data in event details, only identifiers.

### 5. Personal data protection (Proposed, confirm with bank, Q31)
- Classification in `docs/design/data-model.md`: P1 identifiers (CIF, account numbers), P2 contact and demographic data.
- Application-level encryption (key from the secret store, never in the repo) for P1 account numbers and nominee bank details; a keyed hash column supports exact-match lookup.
- Database/disk encryption and role-based access for everything else, as the bank's standards require.
- No personal data in logs, error messages or tokens.
- Raw insurer/CBS payloads, when kept for dispute resolution, are stored encrypted with a retention period set by the bank (Q31).

## Consequences
- More discipline in the data layer, in exchange for a cheap later port to Oracle.
- Audit, sessions and jobs add tables but no extra infrastructure.
- Retention and deletion rules are not set yet (Q31); the schema keeps timestamps needed to apply them later.
