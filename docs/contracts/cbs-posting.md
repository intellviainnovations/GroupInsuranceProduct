# Contract: CBS posting

- **Status:** Proposed shape only. The bank's CBS API specification has not been received (Q27); this contract fixes what the application needs so the spec can be checked against it.
- **Decision behind it:** the application owns every sale. The core banking system is called **only** to debit the customer's account and credit the pool account, and to read the result back (D-023). The CBS is not used for customer lookup in Phase 1.
- **Location in code:** `src/backend/adapters/cbs/` with `base.py` (the port) and `fake/`. The real adapter is written after the spec arrives.

## Port
| Operation | Inputs | Result | Used for |
|---|---|---|---|
| `post_premium` | `cbs_request_ref`, customer account, pool account, amount, narration | `SUCCESS` with CBS transaction id and time, or `FAILED` with a reason, or `UNKNOWN` | Debit the customer and credit the pool account for one enrolment |
| `post_refund` | same, reversed direction, link to the original posting | same | Refund after a cancellation |
| `get_posting_status` | `cbs_request_ref` or transaction id | `SUCCESS`, `FAILED` or `NOT_FOUND`, with transaction details | Resolving an `UNKNOWN`, reconciliation |
| `get_pool_statement` | pool account, business date | list of credits and debits with transaction ids, amounts, times, narrations | Daily reconciliation against our postings |

## Rules
1. **Idempotency:** `cbs_request_ref` is generated by us and unique (`cbs_posting.cbs_request_ref`). A repeat call with the same reference must never post twice; if the CBS cannot guarantee that, we always call `get_posting_status` first.
2. **Never retry a debit blindly.** `UNKNOWN` (timeout, dropped connection) is resolved by `get_posting_status`. If that is also unclear the enrolment goes to `NEEDS_ATTENTION` and operations resolve it with the bank.
3. **Amount:** must equal the premium returned by the insurer for that proposal; the application refuses a posting that does not match (a human resolves plan-rate mismatches, Q30).
4. **Order:** consent is captured first, then the posting, then the insurer's `issue_policy` with the posting details. The posting never happens before the insurer has created the proposal.
5. **Narration:** carries our reference only; no personal data.
6. **Authorisation:** the posting is made on behalf of the signed-in user; the maker-checker rules (Q32) apply before this step.
7. **Failures leave a trace:** every attempt writes a `cbs_posting` row and an `audit_event`.

## Open points (Q27)
API specification and test environment; authentication and payload protection; whether debit and credit are one transaction with two legs or two calls; reversal and refund calls; transaction id, date and time formats; whether the CBS validates the customer account and returns the account holder name; statement format for the pool account; cut-off times and holiday behaviour; limits.
